## 2. The Bug

### What was wrong

`src/evaluate_pipeline.py` runs Stage 2 as a regression model. The continuous output is binned into tier indices using thresholds derived from training-split tier means sorted by ascending price:

```python
tier_means = df.groupby("value_tier")["normalized_log_price"].mean().sort_values()
```

This produces ascending-price ordering: `budget < mid_range < premium < investment_grade`.

The integer tier index from `pred_to_tier` was then used to index into a `TIER_LABELS` constant defined as:

```python
TIER_LABELS = ["budget", "investment_grade", "mid_range", "premium"]   # alphabetical
```

The two orderings disagree on three of four positions. Mapping was:

| Index (ascending price) | Should be | Was assigned |
|---|---|---|
| 0 | budget | budget (correct) |
| 1 | mid_range | investment_grade (wrong) |
| 2 | premium | mid_range (wrong) |
| 3 | investment_grade | premium (wrong) |

### Confirmation

Verified the price ordering directly from `combined_all_train.csv`:

| value_tier | mean log-price (normalized) | mean price USD |
|---|---|---|
| budget | -1.211 | $729 |
| mid_range | -0.034 | $2,532 |
| premium | 0.957 | $6,590 |
| investment_grade | 1.772 | $19,127 |

`tier_label` integer column in the splits is keyed in this same ascending-price order (0=budget, 1=mid_range, 2=premium, 3=investment_grade). Standalone `train_regression_combined.py` compares regression-derived integer tier indices directly against `tier_label` — internally consistent, so its reported tier F1 of 0.6459 was correct. Only `evaluate_pipeline.py`, which converts to string labels and compares strings, was affected.

## 9. Lessons

The bug survived because:

- Standalone Stage 2 metrics (computed against integer `tier_label`) were correct, so there was nothing to compare against until the pipeline eval was done.
- The pipeline eval ran cleanly and produced a sensible-looking JSON. Stage 2 F1 of 0.298 in cross-retailer evaluation is low but not absurd given the cross-domain literature.
- The label ordering assumption was implicit. Nothing in the code asserted that `TIER_LABELS` order had to match the threshold-induced ordering.

The diagnostic that caught it was comparing pipeline Stage 2 F1 (0.298) against standalone combined_all regression Stage 2 F1 (0.646) — a 35-point gap on the same model and same test set was implausible. Once that gap was flagged, the bug was found in a few minutes by reading `pred_to_tier` and `TIER_LABELS` together.

A defensive change worth considering for any future regression-to-tier code: define the tier name list adjacent to the threshold-computation code, derive it from the same `sort_values()` call, and assert the ordering at module load. Out of scope for this session.

## 12. Tier 1.1 — Stage 2 Tier-Threshold Recalibration

### Approach

The original `compute_tier_thresholds` set tier boundaries at the midpoints between training-split tier means in normalized log-price space. These are unbiased but not F1-optimal — the per-tier F1 distribution showed `mid_range` was being under-predicted (recall 0.63) and `premium` over-predicted (precision 0.40).

To improve without retraining or re-running inference, the existing `pipeline_eval_detail.csv` was re-used:

1. Recover the continuous regression output `s2_pred_norm` for every sample by inverting `denormalize_to_usd`: `norm = (log(usd) - mean[subset]) / std[subset]`. Verified by re-binning under the old thresholds and confirming the resulting macro F1 (0.6435) matched the corrected May 2 result.
2. Stratified 50/50 split (by subset × true tier, `random_state=42`) of the 87,037 routed-and-priced rows into a calibration half (43,518) and a held-out validation half (43,519).
3. Coordinate-descent on the calibration half over the three threshold cutpoints. 401-point grid per cutpoint, bounded by neighbors. Converged in 1–2 outer passes.
4. Reported results on the held-out validation half — clean, no test-set leakage from the optimization.
5. Applied the calibration-fit thresholds to the full 89,557-image test set for the final pipeline JSON.

## 14. Tier 1.3 — Stage 1 Routing Rule

### Approach

Stage 1 routing was `argmax == Diamond`. ja_natural was the worst subset at 90.1% recall — every other subset is ≥ 98%. The hypothesis: many ja_natural diamonds are losing the argmax to a single confuser class but Diamond still has substantial probability mass. If so, a softmax threshold or top-K rule could recover most of the misses without exploding FPR.

Pipeline:

1. Run Stage 1 inference once over all 91,324 images. For each image, save Diamond softmax probability, the rank of Diamond among 68 classes (0 = top), and the top-1 argmax class. Saved to `stage1_softmax_detail.csv`.
2. Sweep two routing strategies on the saved data:
   - **Top-K**: route if Diamond is in top-K predictions
   - **Softmax threshold**: route if Diamond probability > T
3. Report recall and FPR for each, plus per-subset breakdown.
4. For the best zero-FPR rule, run Stage 2 on the additional images that get routed (only ~2.3K), merge with existing predictions, recompute pipeline metrics.

### Sweep results

**Top-K:**

| K | Overall recall | FPR | ja_natural recall | be_lab recall |
|---|---|---|---|---|
| 1 (current) | 0.9719 | 0.000 | 0.9013 | 0.9902 |
| 2 | 0.9977 | 0.0074 | 0.9907 | 0.9989 |
| 3 | 0.9992 | 0.0153 | 0.9962 | 0.9997 |
| 5 | 0.9998 | 0.0294 | 0.9994 | 0.9998 |

**Softmax threshold:**

| T | Overall recall | FPR | ja_natural recall | be_lab recall |
|---|---|---|---|---|
| 0.500 | 0.9666 | 0.000 | 0.8821 | 0.9876 |
| 0.300 | 0.9815 | 0.000 | 0.9318 | 0.9939 |
| 0.100 | 0.9926 | 0.000 | 0.9715 | 0.9978 |
| 0.050 | 0.9955 | 0.000 | 0.9827 | 0.9986 |
| **0.020** | **0.9977** | **0.000** | **0.9909** | **0.9992** |

`T = 0.02` is the chosen rule. It catches 99.77% of all diamonds (vs. argmax 97.19%) and recovers ja_natural from 90.13% to 99.09% while holding FPR at literal 0% — not a single non-diamond test image scored above 2% Diamond probability. This is a strict improvement over both argmax and top-2 (which has 0.74% FPR).

### Why ja_natural was the outlier — confusion analysis

For the 1,595 ja_natural diamonds Stage 1 missed under argmax, the top-1 prediction was:

| Confused with | Count | Share |
|---|---|---|
| **Pyrite** | 1,540 | 96.6% |
| Citrine | 27 | 1.7% |
| Andradite | 7 | 0.4% |
| Topaz | 6 | 0.4% |
| Sodalite | 5 | 0.3% |
| (other 65 classes) | 10 | 0.6% |

## Tier 2.1 — Stage 1 fine-tune to reduce Pyrite confusion

### Goal

Reduce ja_natural Diamond → Pyrite confusion (1,540 / 1,595 = 96.6% of all ja_natural Stage 1 misses). Stage 1 was originally trained on `Combined-P1-Dataset/train/Diamond/` (524 studio-quality images), which underrepresents the retailer-style appearance of ja_natural diamonds (16,154 in test). The single fix with the most leverage is to inject retailer-style diamonds into Diamond-class training and warm-start fine-tune.

### Design (revised after advisor review)

The original recipe ("missed test images + correctly-classified test images + Pyrite") was rejected on two grounds:

1. **Test-set leakage.** Fine-tuning on any portion of `combined_all_test.csv` makes before/after pipeline metrics non-comparable. Pivoted to using `combined_all_train.csv` ja_natural rows (74,864 images, fully disjoint from test) as the Diamond-class augmentation source.
2. **Three-class collapse.** Training on only Diamond + Pyrite + missed-ja_natural would wreck the other 66 logits. Pivoted to keeping the full 68-class `Combined-P1-Dataset/train/` ImageFolder as background; only the Diamond class gets augmented.

## Tier 3.3 — Hi-res Stage 2 retrain at 384×384 (SUCCESS)

### Approach

Hypothesis from the Tier 2.2/3.2 negative results: the premium F1 ceiling at 0.49 might be resolution-limited rather than fundamentally information-theoretic. Test it directly: bump Stage 2 input from 224×224 to 384×384 (~3× more pixel area), keep Stage 1 at 224, hold every other variable (architecture, init, loss, optimizer, scheduler, transforms otherwise) constant.

### Implementation

- New script `src/finetune_stage2_hires.py` — fork of `finetune_stage2_balanced.py` with `Resize((384, 384))`, batch_size 48 (10.6 GiB peak vs 13.9 GiB at bs=64), plain shuffle (no class-balanced sampler), ImageNet init, otherwise identical to the original Stage 2 trainer. Added `--init-from <path>` flag for warm-starting (used during the resume).
- `src/evaluate_pipeline.py` extended:
  - `make_transform(size)` factory; `transform_s1` and `transform_s2` are independent.
  - Datasets yield `(img_s1, img_s2, ...)`; `collate_fn` stacks both.
  - `run_inference` routes `imgs_s1` to Stage 1 and `imgs_s2` to Stage 2.
  - New `--stage2-input-size` arg (default 224 — backward compatible). Set to 384 to enable the dual-resolution path.
  - Sized memory before launch: at 384, training peak 10.6 GiB at bs=48; throughput ~303 img/s; ~16-19 min/epoch.

**Phase 1** (epochs 1-6, ~2 hrs): launched cleanly, ran 6 epochs at ~19.7 min each.

- Halted at epoch 6 by user (free GPU resources). Best/last/log preserved as `*_phase1.*`.

### Reading the result

The Tier 2.2/3.2 negative results led us to hypothesize an information-theoretic ceiling on premium F1 at 0.49. **That hypothesis was wrong.** Tier 3.3 broke the ceiling cleanly on test (premium F1 0.49 → 0.53), and the lift extended to every other class and every subset. The bottleneck was resolution, not visual signal availability — the signal *was* there, just sub-pixel at 224×224.

Most striking single number: ja_natural USD MAE dropped $468 — the worst-performing retailer subset became dramatically more accurate. Plausibly because ja_natural retailer photos contain fine surface and clarity detail that 224×224 was washing out.
